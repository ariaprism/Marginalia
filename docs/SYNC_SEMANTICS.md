# Marginalia 本地优先同步语义

> 状态：已确认，作为 Phase 2 schema、RLS、私有 Storage、outbox 与同步引擎的产品语义依据。
>
> 这份文档先用书房语言说明“什么跟着书走、什么时候收进云端、两台设备怎样相遇”。末尾附小G施工时需要的技术翻译。

## 1. 一句话原则

IndexedDB 是眼前正在使用的书桌；Supabase 是长期保存并让小狐狸和小鱼相遇的云端书房。

- 阅读、翻页和写批注永远先在当前设备完成，不等待网络。
- 在线时，新变化通常在几秒内自动收进云端。
- 云端出现的新变化也会自动回到当前设备。
- “本地优先”不是只从本地向云端备份，而是双向流动、操作不被网络阻塞。

## 2. 哪些内容跟着书走

以下内容应该进入云端，并在其他设备登录后恢复。

### 2.1 书籍本身

- EPUB 原文件。
- 封面。
- 书名、英文名、作者和简介。
- 想读／在读／已读完状态。
- 置顶状态。
- 加入书房和最近主动打开的时间。
- 解析后的章节身份与目录；是否保存完整解析结果等实际施工时再按性能决定。

如果没有 EPUB 正文，未来 MCP 就无法让小鱼继续向前后翻阅，所以完整书的原文件必须进入私有云端存储。

### 2.2 书页上的痕迹

- 划线。
- 小狐狸的批注及其修订、删除。
- 小鱼留下的文字。
- 每本书唯一的手动折页。
- 原文定位信息。定位信息只供 Marginalia 内部使用，不直接塞给小鱼。

设备 A 在第一章新增一条批注，设备 B 在第二章新增另一条批注，这两条拥有不同身份，不会互相覆盖。同步后两台设备都会拥有两条批注。

### 2.3 名帖

- 小狐狸的落款。
- 共读者的名字、称呼和人称。

名帖决定批注署名和 MCP 里的共读者身份，建议跟随云端书房，而不是换设备后重新填写。

## 3. 最近停留要不要同步

建议同步，但要把它分成两层理解。

### 当前设备上的阅读位置

每次正常翻页都立即保存在本地，这样刷新或意外关闭不会丢位置。

### 云端里的“最近真正读到”

正常阅读产生的新位置经过短暂防抖后同步到云端，不需要每翻一页都发一次网络请求。返回书架、应用进入后台和恢复网络时也会尝试收好。

同步它有两个价值：

1. 小狐狸换设备后能从最近位置继续。
2. 小鱼可以知道小狐狸最近真正停在哪里，以及哪些章节还没有到达。

目录跳转、查看旧痕迹和临时翻章仍然不覆盖“最近停留”，沿用现在已经确定的产品语义。

如果两台设备都在阅读同一本书，以时间更晚的那次真实阅读为准。云端保存的时间必须来自实际阅读动作，而不是“哪台设备晚几秒完成同步”，避免慢网络把旧位置冒充成新位置。

## 4. 哪些内容只留在当前设备

以下内容暂不需要同步：

- 正文字体。
- 字号。
- 行距。
- 页边距。
- 日间／夜间主题。
- 当前打开了哪个菜单、弹窗或抽屉。
- 书架当前使用列表视图还是封面视图。
- 当前筛选“全部／想读／在读／已读完”的哪一栏。
- 动态页码。EPUB 排版随设备变化，页码不能作为跨设备定位。

这些属于“这台设备上怎样读起来舒服”，换设备后保留各自设置更自然。

## 5. “待寄出的清单”是什么

`outbox` 可以理解为“待寄出的清单”。

例如小狐狸离线时写下一条批注：

1. 批注立即写进本地书页，所以界面马上显示。
2. 同时在待寄出的清单里放一张小纸条：“把批注 A 收进云端”。
3. 网络恢复后，小G的同步程序照着纸条寄出。
4. 云端确认已经收好，才把这张纸条划掉。

如果发送途中断线，纸条仍然留着，稍后重试。每张纸条都有唯一编号，所以同一张纸条即使寄了两次，云端也只收一份。

本地常见动作对应的纸条包括：

- 藏入／修改／移出一本书。
- 新增／修改／删除划线或批注。
- 移动／取消折页。
- 更新最近停留。
- 修改名帖。

小鱼通过 MCP 写入云端的文字不需要先进入小狐狸的待寄清单；网页会从云端把它取回，再保存进本地 IndexedDB。

## 6. 什么时候自动同步

主要依靠动作触发，而不是每几小时才整体同步。

### 本地变化推向云端

- 写入批注、划线或重要设置后的几秒内。
- 藏入书籍后；EPUB 文件可独立在后台上传，不阻塞阅读。
- 网络恢复时。
- 打开应用时。
- 应用从后台回到前台时。
- 返回书架或应用进入后台时。
- 用户在云端书房手动点击同步时。

### 云端变化回到本地

- 打开应用时。
- 应用回到前台时。
- 网络恢复时。
- 网页打开期间收到云端变化提示时。
- 用户手动同步时。

实时通知只负责“快一点知道”，不能作为唯一保障。即使休眠时错过通知，下次打开应用仍会补齐遗漏内容。

每几小时的周期检查可以作为保险，但不能承担主要同步职责。

## 7. 两台设备同时使用时会怎样

大多数动作不会冲突，因为它们是在增加不同的东西。

### 不冲突的例子

- 设备 A 在第一章新增批注 A。
- 三分钟后设备 B 在第二章新增批注 B。
- 两条批注分别进入云端。
- 随后 A 和 B 都显示批注 A 与批注 B。

### 真正会冲突的少数情况

只有两台设备在尚未看到对方修改时，同时改动“同一个东西”，才需要选择：

- 同时修订同一条批注。
- 同时移动同一本书唯一的折页。
- 同时修改同一本书的书名或简介。
- 同时更新同一本书的最近停留。
- 一台设备删除某条批注，另一台仍在修订它。

第一版不做复杂的合并界面，采用简单规则：

- 新增内容各自保留，不互相覆盖。
- 同一条批注的修订，以实际修改时间更晚者为准。
- 唯一折页，以实际移动时间更晚者为准。
- 最近停留，以实际真实阅读时间更晚者为准。
- 删除优先于删除发生前的旧修改；另一台设备不能因为晚同步而把已删除内容重新带回来。

若以后真实使用中出现需要保留两个版本的情况，再增加修订历史；Phase 2 第一版不提前制作复杂冲突工具。

## 8. 小鱼通过 MCP 怎样参与

未来 MCP 连接云端书房，而不是直接连接某一台浏览器。

### 小狐狸写下批注

```text
写入本地书页
→ 放入待寄出的清单
→ 在线时几秒内进入 Supabase
→ 小鱼通过 MCP 看见
```

### 小鱼留下文字

```text
小鱼调用 MCP
→ MCP 写入 Supabase
→ 打开的网页收到变化提示并拉取
→ 写入本地 IndexedDB
→ 小狐狸在书页上看见
```

如果网页当时关闭，小鱼的文字先安静地留在云端；小狐狸第二天打开书房时自动取回。

无法绕过的边界是：若小狐狸离线写完后立即关闭应用，批注从未到达云端，MCP 就不可能提前知道它。界面应明确但克制地显示还有多少内容没有收进云端。

## 9. 删除为什么不能只在本地抹掉

假设设备 A 删除一条批注，而设备 B 当时离线。如果云端只看到“这条数据不见了”，不一定知道它是被删除还是还没上传。

因此删除后需要暂时留一张“已经删除”的记录，让其他设备收到后也删除。这张记录可在所有设备确认后或经过保留期再清理。

对小狐狸来说仍然只是正常的“抹去文字”；这是 Marginalia 内部防止旧内容复活的机制。

## 10. 普通同步与“从云端恢复”不同

### 普通同步

只交换上次以后发生的变化，合并进当前书房，不覆盖尚未寄出的本地内容。这是每天自动发生的流程。

### 从云端恢复

用于换设备、本地数据库损坏或用户明确重建书房。它会重新下载书籍、文件和痕迹，属于需要确认的特殊操作。

恢复前如果当前设备仍有未寄出的内容，必须先提示并尝试同步，不能静默覆盖。

## 11. 云端书房怎样表达状态

状态集中放在侧边栏“云端书房”的小字区域，不在阅读页持续打扰。

建议文案：

- `书房只留在这台设备`：尚未连接云端。
- `墨迹已收好 · 刚刚`：本地与云端一致。
- `还有 2 道墨迹未干`：存在待寄出的变化。
- `正在收好书页…`：正在同步。
- `暂时收不到云端`：离线或同步失败，本地写入仍安全。
- `昨夜带回 2 道文字`：从云端取回了小鱼的新文字。

这里可以同时提供低调的“立即收好”按钮和最后成功同步时间。日常不使用社交式红点。

## 12. 已确认的补充决定

1. 同一条小狐狸批注允许小鱼在不同来访中留下多条文字。不同时间的重访各自保留，不覆盖成一条线性回复。
2. 置顶状态跨设备同步。
3. 书架最近主动打开时间跨设备同步，书架排序反映整个云端书房最近真实发生的阅读活动。
4. Phase 2 第一版不提供“仅在 Wi-Fi 上传 EPUB”。等真实手机上传体验表明有需要时再增加，不提前扩大设置面板。

## 13. 给小G施工用的技术翻译

下面这些术语不要求小狐狸阅读或决定，只是把上面的产品语义固定成后续实现约束。

- IndexedDB 是 UI 的读取与第一写入点。
- 本地 mutation 与 outbox item 必须原子写入，不能出现数据写成但待同步记录丢失。
- 每个实体使用跨设备稳定 ID；每次同步操作使用唯一 idempotency key。
- 推送成功必须以远端确认结果为准，不能发出请求后立即清 outbox。
- 拉取使用单调的远端变更游标；Realtime 只触发拉取，不替代游标。
- 删除使用 tombstone，避免离线设备把旧记录重新上传。
- 新增型实体按 ID 合并；同实体更新第一版按 `modified_at` 采用 last-write-wins。
- 阅读位置额外保存 `read_at`，冲突比较真实阅读时间，不比较请求抵达服务器的时间。
- 折页移动保存 `moved_at`；同书唯一折页采用最新移动事件。
- 完整恢复与日常增量同步必须是两个不同入口和代码路径。
- MCP 写入包含 actor、session、idempotency key 与服务端时间，并进入同一条远端变更流。
